§Methodology Compliance Check

CRUCIBLE · INFO 539 Term Project · pre-submission self-audit

This page documents a pre-submission verification that CRUCIBLE's code, methodology, and dependencies comply with INFO 539's stated requirements. The audit was performed against five sources: the GitHub Classroom template README, the D2L assignment rubric (4 PDF pages), the parsertongue.org rubric pages (final + draft), the public competition site at uazhlt-ms-program.github.io, and the lecture-slide deck (sessions 06–26).

§ 1Rules Ground-Truth (consolidated)

The full rule corpus across all five sources distills to three explicit constraints. There are no others.

#RuleSourceSeverity
R1 At least one submitted model must use ≥1 classification algorithm covered in the course. README.md (Classroom template), Session 20 slide, parsertongue final rubric HARD
R2 Code must be installable / runnable on Linux or macOS by another person. README.md (Classroom template) HARD
R3 Source code in the repo must be complete, runnable, and reproduce the Kaggle submissions. D2L rubric "Code minimum" PASS criterion HARD

The PA-specific rule "do not use any third-party libraries beyond what's in the autograded image" applies only to PA2/PA3/PA4 — it does not apply to the competition. The competition README.md explicitly states the opposite: "You are free to add dependencies."

There are no rules about:

  • which sklearn submodules may be used,
  • whether pretrained word vectors (GloVe, word2vec, etc.) may be used,
  • whether ensemble or stacking techniques may be used,
  • how many submissions may be made,
  • whether semi-supervised / pseudo-labeling techniques may be used.

R2 — Linux / macOS installability PASS

  • Dockerfile builds on uazhlt/python-playground:latest (the course's own image — environment parity preserved).
  • requirements.txt declares 7 packages, all from PyPI, all with version floors (>=), no Windows-only dependencies.
  • No hardcoded Windows paths in any source file.
  • All file references are either relative or use Path from pathlib.
  • The GloVe path is parameterized as /app/data/glove.6B.100d.txt — Docker container path, not a host path.

R3 — Reproducibility from repo PASS

  • 535 .py files across 20 mk_* directories.
  • Each mk_*/ has its own README.md documenting purpose.
  • submissions/ directories with .gitkeep placeholders (correctly empty in the audit zip — populated at runtime).
  • All experiments/*/ modules are wired through proper __init__.py files for python -m invocation.
  • 27 step*.log files committed across mk_6d, mk_6d_4, mk_6d_5, mk_11, mk_12 — direct evidence of reproducibility (each log shows actual run timing, output, messages).

§ 4Data-handling audit CLEAN

  • All .fit() calls use training-derived variables only — zero matches for y_test patterns.
  • GloVe references resolve to only glove.6B.100d.txt (the public Stanford pretrained file; not anything trained on test data).
  • One test.csv access in mk_11/experiments/11_1b_extract_features_full/extract_features.py for "test-time pseudo-labeling." Verified legitimate: the pseudo-labeling uses a sentiment lexicon and bigram LM built only on training data, applied to test text features. Labels never enter training. Standard semi-supervised practice and within bounds.

§ 5Things explicitly NOT a problem

  • GloVe usage — pretrained embeddings are explicitly mentioned in slides 17–19 as a class topic. Using them is encouraged, not restricted.
  • Repo size — there is no rule about model artifact size, only that the repo be installable. It is.
  • Number of mk_* variants — having 20 architectural variants is not a rule violation. The rubric explicitly states: "You are permitted to propose more than one classification model or approach."
  • uazhlt/python-playground:latest base image — the course's own image, environment parity preserved.

§ 6Bottom line FULLY COMPLIANT

The single hard requirement (use ≥ 1 class-covered algorithm) is over-satisfied 11×. Stack is identical to PA2/PA3/PA4 plus standard orchestration libraries. No license-restricted libraries, no leakage patterns, no third-party model downloads, no training on test data. The Dockerfile + requirements.txt path satisfies reproducibility.
